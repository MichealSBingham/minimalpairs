## Recommended architecture and fixed costs

Keep static hosting, Firebase Auth and Firestore on Spark. Add a thin Cloudflare Worker for authenticated checkout/portal endpoints and signed webhook intake, backed by a SQLite Durable Object for a private billing ledger and durable retry processing. Stripe-hosted Checkout collects card details; Stripe's hosted portal handles payment-method changes and cancellation. Only the server writes subscription entitlements to Firestore. No Firebase Functions, separate email vendor, paid portal domain or always-running server is required by this design.

## What the isolated module implements

`core.mjs` contains HTTP request policy, exact-byte HMAC verification, recurring-access policy, event processing, and bound-customer canonical reconciliation orchestration. `config.example.json` supplies blank identifiers and false switches. `runtime/worker.mjs`, `runtime/ledger.mjs` and `wrangler.jsonc` provide a disabled production entry, SQLite ledger and configuration. Implemented providers are documented in [Firebase validation](providers/firebase.md) and [Stripe validation](providers/stripe.md). There is no app import of the backend or committed provider credential. Production Firebase ports require live Stripe mode; test ports require the fixed separate Sandbox project. `wrangler.sandbox.jsonc` prepares a distinct disabled Worker/ledger; it is not deployed.

- Checkout accepts only a plan name and request UUID, requires a trusted verified account, and selects server-configured USD monthly/annual price IDs, quantity one, card payment and fixed return URLs. No trial, discount or arbitrary price/customer/UID can be supplied by the client.
- Server-owned UID → customer mapping is checked against Stripe customer metadata and test/live mode. Email lookup never becomes a customer-binding mechanism; a billing email change never changes Firebase identity.
- Before external creation, the durable port reserves opaque operation IDs. Customer retries retain original creation parameters. Checkout retries retain the exact parameters, operation key and timestamp even after a new client request. Config drift stops reuse. Ambiguous creation older than 23 hours requires reconciliation rather than blindly replaying a potentially expired Stripe key; Stripe can prune keys after 24 hours. [Stripe idempotency](https://docs.stripe.com/api/idempotent_requests).
- Any nonterminal existing subscription blocks another checkout. Known open checkouts are reused; an expired one can be replaced. A completed checkout is retired only after its exact subscription/customer/UID/mode is represented in canonical reconciliation, so canceled customers can later resubscribe. Unknown creation outcomes remain blocked until reconciled.
- Webhooks verify bounded raw bytes, `v1` HMAC, a five-minute timestamp window and expected Stripe mode before parsing their event. Connect-account events are rejected. Up to two secrets permit rotation. Intake stores only event/object IDs, type and timing, then acknowledges only after the durable port commits. No checkout-return or `checkout.session.completed` event directly grants access.
- Processing deduplicates event IDs, fetches current customer subscription/payment state, projects it, and only then marks the event processed. Failed storage/network operations remain pending. A crash after projection re-fetches current state on retry. The old event timestamp/payload never decides the grant. Stripe delivery can be duplicated or out of order; live automatic retries last up to three days. [Stripe webhook behavior](https://docs.stripe.com/webhooks).
- Periodic recovery checks already-bound customers independently of event delivery, through the same canonical projection and exact checkout retirement path. Its six-hour successful-check cadence can recover a missing renewal/refund webhook; failures retain exponential backoff. Recovery latency can exceed the cadence under outages or backlog. Unbound ambiguous customer creation remains outside this sweep. This background sweep creates no synthetic event. A separate explicit authenticated checkout-status request is described below.
- An explicit authenticated `POST /billing/checkout-status` accepts only an empty body and returns an allowlisted state for the verified account. It shares the durable checkout/reconciliation lock, checks existing subscriptions and exact Stripe customer/session ownership, and retires only a provider-confirmed expired session. Unknown creation outcomes remain reserved. It creates no customer, checkout, subscription or entitlement and sends no messages. The client may clear its pending note only for a confirmed `none` result or fresh purchased access; open/pending responses restore the canonical server request across devices. Stopping new sales does not prevent this recovery check.
- Portal URLs use only the bound customer, an explicit portal configuration and fixed return path. Only genuine hosted Stripe URL hosts are accepted. Stopping new sales uses `checkoutEnabled=false`; keep the operating service/webhooks/portal available for existing customers. The broader service switch also blocks background processing and is not a normal sales toggle. [Hosted portal integration](https://docs.stripe.com/customer-management/integrate-customer-portal).

## Proposed access/refund policy, to match the eventual terms

Access requires an approved one-item subscription plus current positive paid coverage from a successful charge. `active` by itself is insufficient. A `past_due` subscription retains only any still-paid period; there is no unpaid grace period in this initial policy. `trialing`, `incomplete`, `paused`, `unpaid` and `canceled` do not grant access. Scheduled cancellation retains the paid term; immediate cancellation ends it. Stripe can report a subscription active even when invoices have not actually been paid, so the normalized invoice/charge evidence matters. [Subscription lifecycle](https://docs.stripe.com/billing/subscriptions/webhooks).

A full successful refund for the current period, or an open/lost dispute on that payment, excludes that coverage. Partial refunds retain it; a won dispute can restore paid coverage. A refunded older period does not revoke a separately paid current period. This is a staged business rule, not published policy or a refund action. Refunds and subscription cancellation are separate in Stripe: a full refund alone does not stop future renewal. The complete operating workflow must explicitly decide and test renewal cancellation and review restoration before launch. No automatic refund/cancel operation exists here. [Stripe cancellation behavior](https://docs.stripe.com/billing/subscriptions/cancel).

The first implementation sells immutable configured prices. Changing those IDs requires a versioned historical price allowlist and migration plan before deployment; simply replacing the price would wrongly invalidate existing paid subscriptions. Initial portal configuration should allow payment-method updates and end-of-period cancellation, with subscription switching/quantity changes disabled until proration and historical-price policies are implemented. No customer grant can override the seven lifetime records.
